LHB-87, Codex round 1 BLOCK and its fix (2026-10-28 about 16:50Z).
Finding: with a short wide map (Codex's harness: 536 x 185), tapping a group could stall: fitBounds with 48 px padding a
side cannot raise the zoom, and neither popup condition (zoom 17, all places on one spot) held, so the tap did nothing.
Fix: tapGroup(z, fz, one) in site/app.js; the handler passes fz = map.getBoundsZoom(bounds, false, L.point(96,96)), the
zoom fitBounds({padding:[48,48]}) would reach (Leaflet sums the top-left and bottom-right padding). A tap zooms only when
min(fz,17) > z; otherwise it lists the group's places in the popup.
Regression test (test/site.test.js, "tocar grupos con los lugares de verdad"): the real places, an opening zoom from the
same fit as drawMap (padding 28 a side, max 11), Leaflet's getBoundsZoom rule re-implemented on Web Mercator (zoomSnap 1,
floor), maps of 536x185, 360x300, 412x260, 800x420 and 1200x500; every group is tapped until it lists or splits, each
zooming tap must raise the zoom, and every place must end single or listed. Approximation, stated: after a zoom the
simulation lays out only the tapped group's places, not their new neighbours.
Proof that it catches the defect: with tapGroup reduced to the round 1 rule (M13 in lhb-87-mutations-r1fix.py) and the
unit assertions removed, the simulation alone fails: "un toque que acerca sube el zoom (536x185: 8 a 8)".

Live read on the fix's preview (https://dbbf05c5.la-hoja-boricua.pages.dev/#/lugares, c20bd16), built-in browser with the
viewport emulated at 536 x 400 so the map is 502 x 230 from load (map-wrap height is vh-based), about 17:00Z. The pane was
hidden, which pauses Leaflet's animation frames; a screenshot after each tap let the zoom finish (an earlier read without
that showed no change at all and was an instrument artifact, not a stall). Sequence, tapping the largest group each time:
opening view groups 23,2,4,3,3,3 (3 single pins); tap 23 -> groups 20,2,2,3,2,2,2 (8 pins); tap 20 -> groups
2,17,3,2,2,2,2 (11 pins, tiles at zoom 10); tap 17 (twice: the first read came before its zoom settled) -> tiles at zoom 11
and a popup listing 17 place cards (.pop), starting "Don Rey Cigar (Viejo San Juan)", "Casa de Montecristo". So the group
that would have stalled ends in a list. Not exercised live: the exact 536 x 185 size (CSS does not produce it at load).

Codex round 2 BLOCK (evidence/lhb-87-review-r2.txt): the list popup's maxHeight 320 could exceed a short map, and
.map-wrap clips overflow, so the last cards' links were unreachable. Fix (8a56c9a): popMaxH(h) = clamp(h - 104, 60, 320),
104 = the popup's fixed chrome (content margins 24, wrapper 2, tip 19, popup margin 20, offset 7, autoPanPadding 32),
summed from the CSS and Leaflet rules in the test; the list popup passes map.getSize().y.
Live read on its preview (https://a722dd2f.la-hoja-boricua.pages.dev/#/lugares), viewport 536 x 400, map 502 x 230.4,
about 17:10Z: a group list popup of 23 place cards; content clientHeight 126 (= 230 - 104), scrollHeight 4986; the popup
wrapper spans y 347.0 to 499.0 inside the map's 337.0 to 567.4; after scrolling the content to its end, the last card's
last link spans y 408.6 to 444.6, inside both the content box (bottom 486.0) and the map. So every card's links are
reachable. A 126 px window over 23 cards is a narrow scroll; the list view (Lista) shows every place in full.

Codex round 3 BLOCK (evidence/lhb-87-review-r3.txt): the list popup's cap was computed once, at the tap; resizing the map
with the list open (a phone turned) left the old cap and clipped it. Fix (469ff16): fitPop(map, p) sets maxHeight from
popMaxH(map.getSize().y) and calls p.update() (Leaflet's DivOverlay.update: content, layout with the current maxHeight,
position, then _adjustPan) while the list is still open; drawMap keeps the list as listPop and runs fitPop on map
'resize'. Round 3's nonblocking P3, kept as is: POP_FIXED 104 is conservative (the tip sits partly in the 20 px margin),
so it errs toward a shorter list, and the 60 px floor can still overflow on maps under about 90 px, which the CSS
(.map-wrap min(58vh,460px) / min(46vh,360px)) reaches only on viewports under about 200 px tall.
Live read on its preview (https://034e202f.la-hoja-boricua.pages.dev/#/lugares), about 17:28Z, map scrolled into view so
Leaflet's frames run (the pane was hidden): viewport 536 x 400 (map 230): taps 23 -> 20 -> 17 -> 7 -> a group of 2 at
one spot, whose tap opened a list popup of 2 cards, content 126 px, wrapper y 127 to 279 inside the map's 85 to 315.
Then, with the popup open, the viewport was set to 536 x 330: map 190, content 86 px (= 190 - 104), wrapper y 112 to 224
inside the map's 70 to 260. So the open list refits to the new height.
Observation, not a defect claim: in an earlier pass I tapped a group again while its zoom animation was frozen by the
hidden pane; the popup then opened at the group's pre-zoom spot and ended above the map once the zoom finished
(wrapper 282 to 434, map 337 to 567). With frames running, Leaflet's zoom animation lasts about 250 ms; whether a tap in
that window can do this for a person is NOT VERIFIED.
