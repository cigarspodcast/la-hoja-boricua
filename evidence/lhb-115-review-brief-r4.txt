Code review, LHB-115, TIER 2, round 4. Repository cigarspodcast/la-hoja-boricua, branch lhb-115-espanol (round 1 named it lhb-115-lang by mistake). You are reviewing; do not edit files.

The ticket (owner, 2026-10-30): the app defaults to Spanish, with the choice of changing languages. On the first visit a full-screen choice comes before anything else, including the intro video. The choice is remembered in a cookie for later sessions, and when the person is signed in their language is saved to the account.

Pinned decisions:
- With no saved choice, the browser language is not read; the app is in Spanish.
- On the first visit with no saved choice, a full-screen choice ("Español" or "English", each in its own language) comes before anything else, the intro video included. It is saved to the cookie and localStorage and applied at once.
- Signed in: the choice is saved to the account. A change from the menu also updates the account. AMENDED after round 3, see below: the device's choice is what counts; the account keeps a copy and is read only when the device has no choice.
- The menu's language switch stays. The privacy page says a cookie remembers the language.

Round 2 (evidence/lhb-115-review-r2.txt, on 14eb3d1) concurred with R1-1, R1-3, R1-4 and R1-5. It maintained R1-2 through four new P2 findings, all against the pending marker, plus R2-5. The marker is gone. The design is now:
- Device versus account. cuenta.js syncLang(C,uid,profile,fresh). fresh means this is a sign-in on this device: no cached profile of this uid existed before this /api/me answer. Sign-out clears that cache, and so does a different account (LHB-51).
  - fresh: the account's language wins, as before (set(acc,{local:true}) or remember).
  - Not fresh (the same account already open on this device): the device's language wins, and if it differs from the account's it is PUT. A menu change whose PUT failed or timed out is therefore not undone by the old account value on the next load; it is resent until the account matches. Codex round 2 noted that this resubmission is bounded by page loads, not a loop.
  - If the device has no choice, the account's applies either way.
  This answers R2-1 (no marker can carry account A's choice to account B: a new account is fresh, so B's value wins and nothing is PUT to B), R2-2's marker half and R2-3 (no marker to write or lose).

- R2-4: onSet no longer requires the cached profile. It runs when there is a cached profile or Clerk's __client_uat cookie is present and not 0, and it PUTs to the account of Clerk's current session (C.user.id).
- R2-5: choosing Español on the first-visit screen also calls LHB_I18N.onSet('es') (fire and forget), so a signed-in account gets it.

Round 3 (evidence/lhb-115-review-r3.txt, on d2b07c3) concurred with R2-1, R2-4 and R2-5, and blocked on four P2 findings. Three of them (R3-1 edit path, R3-2 cookie-only storage, R3-3 a stale account read reversing a chooser choice) come from one rule: "on sign-in the account's language wins". That rule was the planner's own elaboration. The owner's words on the ticket are: "a prompt then that gets recoded in cookies for future sessions - if they are logged in their language preference is saved". With the first-visit chooser, every device has a choice before anyone can sign in, so pulling the account's value at sign-in could only ever override the person's latest choice. The decision is amended (recorded on the ticket):
- cuenta.js syncLang(C,uid,profile): if the device has a choice, it wins; if the account's copy differs, the device's is PUT. Only when the device has no choice is the account's applied (set(acc,{local:true}), or remember when the page already shows it). There is no "fresh" detection, cache dependence or marker. It runs on every signed-in success path, including edit (R3-1), onboarding and identity.
- R3-4: putLang sends one request at a time. A request made while one is in flight replaces any queued value, and when the in-flight request ends only the latest queued value is sent. The account therefore ends with the last choice whatever order the responses arrive in. A hung request blocks further sends in that page only; the next load resyncs.
- Unchanged from round 3: set() reloads once, for the latest change; onSet uses Clerk's current session (cached profile or __client_uat); Español on the chooser calls onSet.
Tests: two red on the round 3 code (evidence/lhb-115-r3-red-before.txt), green after (evidence/lhb-115-r3-green-after.txt). The earlier "account wins on sign-in" expectations are rewritten to the amended rule. Full suite: 500 tests, 499 pass, 0 fail, 1 skipped (evidence/lhb-115-tests.txt).

Also check in this round: anything the amended rule breaks for a person who uses two devices, and whether the account value can still override a device choice through any path (set with local:true is now reached only when the device has no saved choice).
