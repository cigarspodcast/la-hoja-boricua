Round 4 changes (this replaces the R2-1 and R2-3 descriptions below where they differ):
- One ordering rule. A WRITER removes an entry only after it has recorded the base that makes the entry unnecessary: its own landed upload's base (best, written in the ask loop), the poisoned meta when voided or staleBase (shared loop), or the final meta after a 200 (cleanup of entries with r <= the If-Match now runs only after the final writeMeta succeeds; if that fails, the entries stay). A READER, after each GET, reads the entries first (now = shRead(), added to seen) and then reads META again; if it changed, the pass uses the re-read meta (same rules as at the start: same account and epoch). So either the reader sees the entry, or it reads the newer base (R3-1, R3-2).
- Overflow (R3-3): after OPS_ASK entries for one account and rev, every upload, from any tab, goes under one shared key PEND+'x.'+rev+'.'+account, written once (idempotent: tabs writing it at the same moment write the same key). It is never removed because the fence went up (another tab may be sending under it; sign-out sees it and backs out). No tab counts it as its own. At r < rev it voids, unless the pass knows some upload at If-Match r landed (wonAt: an asked upload, this tab's or another's, landed at r+1); since one PUT per If-Match can land, then no other upload at r did. The same rule clears another tab's unanswerable id entry. The per-tab overflow keys and XTABS are gone. Bound: OPS_ASK id keys plus one shared key per account and rev; tabs adding at the same moment can each add one more id key.
- When voided or staleBase and even the poisoned (minimal) meta cannot be written, the pass no longer returns fail 'storage': it keeps the entries (keeping is always safe) and goes on, so a pass that can upload still does (the LHB-31 test 'dos fallos seguidos sin recargar' requires the deletion to be uploaded there). This tab's own entries stay in myOps until they are actually removed.
- R2-2 (fail-closed fence checks in shAdd) and the R2-1 `seen` map are unchanged.

Contract impact: localStorage keys with the prefix lhb_mihoja_v1_pend. (one key per upload), replacing round 1's single lhb_mihoja_v1_pend list (never released, so nothing to migrate).
- PEND+<upload id> = {v:1,s:account,r:If-Match rev,o:id}. Overflow: PEND+'x.'+<rev>+'.'+<account> (shared) = {v:1,s,r,x:true}, no id. A key whose value does not parse as either shape is ignored. A read or write that throws propagates (inside a pass, once()'s wrapper turns it into fail 'storage'; settled() treats it as pending; forget() backs out).
- shAdd (before each PUT): if this account already has OPS_ASK or more entries at this rev, the upload goes under this tab's overflow key (written once); otherwise under its own key. After the write it reads the fence again: if the fence is up, it removes what it just wrote and throws, so the PUT is not sent. forget() raises the fence, waits FENCE_MS, raises it again, checks the mark, and now reads the record again: an entry for the signed-in account or the copy's owner backs out (finding 2). The protocol is two flags: either sign-out sees the entry, or the upload sees the fence. Its cross-process visibility rests on the same assumption as the existing fence (FENCE_MS for a write to reach other tabs).
- Each key is written only by the tab that created it. Any tab removes a key by name: a 409/4xx removes that upload's own key (not an overflow key); a 200 at If-Match rev removes every entry of the account with r <= rev; after a GET, entries with r < rev are removed (finding 1). A tab that rewrites its overflow key after another tab removed it leaves a stale entry, which the next pass judges and removes.
- After a GET: for each entry of the account with r < rev that is not this tab's (myOps for ids; round 4 removed myX) and that the server does not answer as not landed (null and covered by opsFrom), the pass merges with no base (voided); an overflow key cannot be asked about, so it always voids. Before removing those entries, if voided is set, the pass writes the poisoned meta (rev 0, base null, dirty); if that write fails, the pass keeps the entries (finding 3; round 4: and goes on).
- Bound: per account and rev, at most OPS_ASK id keys (plus one per tab adding at the same moment) and one shared overflow key.
- hoja.js gives the engine ls.keys() (localStorage.key(i) over length).
